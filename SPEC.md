# Rebalancer improvements

**Implementation record · November 24, 2026.** The numbered findings below describe the behavior found at `0e6aedd` and the acceptance criteria for its replacement. Items 1–20 are implemented. Live verification of transfer settlement and pending redemption visibility depends on the corresponding broker activity.

Items **1, 2, 4 and 9** cover state publication. Items **3 and 10** protect brokerage inputs. Items **17 and 18** cover transfer valuation and instruction sizing.

## State and sync

**2. Validate the complete set of files eligible for sync.** The validator checks top-level JSON and JSONL files, but both Git paths stage whole directories. A disposable CSV and nested JSON passed validation unchecked. Make local and scheduled sync agree on managed paths and permitted formats. Reject unexpected candidates before staging and verify the content being committed. Test a new valid ciphertext file alongside an unexpected plaintext file, a nested file, and a staged change. The failure must leave the remote untouched. [Encryption boundary](src/encrypted_state.py) · [Local sync](main.py) · [Workflow template](templates/private-state-repo/portfolio_sync.yml)

**4. Preserve the user's Git staging area.** Local sync stages app state and commits the entire index. A previously staged settings edit can ride along with a rotated token. Commit only the validated state paths and detect changes already staged under those paths. Verify with a disposable Git repository and local bare remote: after rotation, the remote contains the new token, the settings edit is still staged locally, and a second sync creates no empty commit. [Local sync](main.py)

**1. Push each replacement token immediately after rotation.** Questrade invalidates the previous token at exchange time. On both local and scheduled runs, atomically save the replacement as ciphertext, validate it, then commit and push just that token file to the private state repository before continuing. Apply this to each login and to a refresh after HTTP 401. Portfolio history and other app state sync together at the end of the run. [Token exchange](src/questrade_client.py) · [Entry points](main.py) · [Scheduled workflow](templates/private-state-repo/portfolio_sync.yml)

If the push fails, report the failure immediately, retain the encrypted replacement and retry publishing that same token without another OAuth exchange. If recovery fails, stop and report that the remote is out of sync. Keep the scheduled workflow's final recovery attempt before the runner exits. Verify with a disposable remote that the first login's replacement is already there when the second login starts, and that a 401 refresh reaches the remote before the API request is retried. A later report failure must leave those tokens available remotely. For a failed push followed by a successful retry, verify one exchange and one token-only commit. [Sync tests](tests/test_main_sync.py) · [Client tests](tests/test_questrade_client.py)

**9. Check the ability to save a replacement token before consuming the old one.** The preflight decrypts existing state. A missing or unusable SOPS creation rule is discovered only when the new token is encrypted, after the broker has invalidated its predecessor. Exercise encryption and decryption with harmless data under each configured token path's rules before the first OAuth request. Verify a missing config, a nonmatching rule, and an unreadable replacement recipient all prevent rotation. A disk or network failure after preflight still needs an explicit recovery message. [SOPS operations](src/encrypted_state.py) · [Token exchange](src/questrade_client.py) · [Existing encryption tests](tests/test_encrypted_state.py)

For **1 and 4**, also test recovery after the local commit succeeds and the push fails. In a disposable repository the next call reported “No local changes to push” while the local branch was one state commit ahead of its remote. Check outstanding commits as well as file changes. Retry a verified app-only fast-forward push and verify remote synchronization. If the branch also contains an unrelated commit or has diverged, identify the unresolved state for the user. [Local sync](main.py)

**20. Parse CLI options before starting a run.** Both `python main.py --help` and a mistyped `--syn` selected the interactive path in a mocked entry-point check, including pull, report and push. A user asking for usage can therefore rotate live credentials. Use the standard argument parser with long-option abbreviation disabled. Verify that help exits successfully and an unknown option exits with a usage error before Git, SOPS or the broker is called. Keep the documented no-argument and `--sync` modes. [CLI entry point](main.py)

## Portfolio inputs and targets

**3. Distinguish unavailable broker data from a real zero.** A missing accounts or positions field becomes an empty list. A missing per-currency balances field valued a synthetic account at zero. Require the expected response collections and finite values for fields used to price a nonzero holding or cash balance. Preserve legitimate empty positions and real zero cash. With two configured logins, a malformed response from either must prevent a household snapshot, tactical evaluation, and drift output. Keep successful token rotations. [Broker client](src/questrade_client.py) · [Portfolio builder](src/portfolio.py)

**10. Count each brokerage account once.** Two connections returning the same account number doubled a synthetic CAD 100 balance to CAD 200. Meanwhile, the planner keys available cash by account number, so valuation and buying power can disagree. Reject duplicate account numbers in the common portfolio builder before any household result is returned. Reject repeated token filenames during config loading as an earlier check for the simplest mistake. Test overlapping account lists with external tracking disabled and two legitimate accounts with the same owner/type. [Portfolio builder](src/portfolio.py) · [Cash ledger](src/rebalancer.py) · [Config loader](main.py)

**5. Validate allocation weights in both modes.** Interactive validation accepts 110% paired with −10%, and accepts a non-finite total. Scheduled accuracy skips the total check. Require finite, nonnegative weights and the existing total tolerance on the final map before calculating trades or publishing accuracy. Validate configured inputs before transformations can conceal invalid values. Test static, FX-derived, and tactical targets, including valid zero weights. A market snapshot can still be useful when targets are invalid, but it must never produce a drift score from those targets. [Run modes and validation](main.py) · [Tactical targets](src/tactical.py)

**6. Preserve the combined allocation of an FX pair.** With a 20% budget, a three-point step, and a midpoint rate, the two rounded weights are 9% and 12%. Round the CAD leg, bound it to the pair's budget, and give the USD leg the exact remainder. The remainder can be off-step when the budget is indivisible. Test both band endpoints and the midpoint, with and without a saved target, including a reduced budget. Preserve sticky rounding and the existing divisible-budget cases. [FX resolver](src/fx_targets.py) · [FX tests](tests/test_fx_targets.py)

## External transfers

**17. Keep withdrawals dated before a recommendation out of its transit balance.** A November 6 recommendation was based on a November 1 statement. The next import included a November 2 withdrawal of CAD 100. The ledger correctly lowered savings by CAD 100, then incorrectly added CAD 100 of transit against the later recommendation. Use the statement date and the cycle start to distinguish earlier movements while still updating the reported balance, observation cursor and lifetime counters. Preserve the existing baseline treatment for ambiguous same-day rows. Verify both transfer directions with a pre-recommendation row, a later qualifying row, and a replay of the same export. [Statement observation and cycle baselines](src/transfer_tracking.py) · [Transfer scenarios](tests/test_transfer_tracking.py)

**18. Count a receipt awaiting its source statement against the existing transfer cap.** In a synthetic CAD 180,000 withdrawal cycle, Questrade had received all CAD 180,000 and the source export was still outstanding. With savings still above target, the planner issued another CAD 180,000 withdrawal. Valuation already recognizes the receipt, but the instruction cap subtracts only source-confirmed principal and other orders in the plan. While awaiting the export, reserve the principal already attributed to this cycle when sizing further instructions. Verify a full receipt produces only the awaiting-export status for that cycle, and a partial receipt permits at most its unused allowance. After the export arrives, re-evaluate any remaining drift and retain the documented treatment of outside-bank top-ups. [Transfer sizing](src/rebalancer.py) · [Receipt accounting](src/transfer_tracking.py) · [Transfer contract](docs/external-accounts.md)

## Planner and reporting

**7. Use actual account funding for projected cash.** A buy that uses existing USD and converts CAD for the shortfall carries a single `requires_fx` flag. Projection charges the whole purchase to CAD and corrects deficits across the household. In the audit example the ledger ended at CAD 67.50 and USD 1,000, but the projection showed CAD 0 and USD 1,050. Apply net trade impacts and conversion amounts per account before aggregating. Use the same funding rules for intermediate drift and the displayed final plan. Verify a mixed-funded purchase, whole DLR shares and fees, FX-funded transfers, and a second account whose cash cannot fund the first. [Planner](src/rebalancer.py) · [Projection](src/portfolio.py) · [Conversion instructions](src/fx_conversions.py)

**11. Remove the holding when the last unit is sold.** Selling all ten CAD 100 units at a CAD 99 bid leaves CAD 10 recorded as a holding and a projected allocation of 1%. Projection subtracts proceeds from a position valued at a different price. Project the units remaining at a consistent valuation price and credit cash at the executable price. Verify the full sale leaves zero units, zero holding value, CAD 990 cash and CAD 990 total. Also verify a partial sale, a buy at the ask, and a position held in two accounts. This belongs alongside 7 because both affect drift in later rounds. [Projection](src/portfolio.py) · [Projection tests](tests/test_portfolio.py)

**12. Carry existing currency debits through funding.** With CAD 135, USD −50, and a fee-free CAD 1.35/USD conversion, the planner recommended a USD 100 buy. The conversion instructions deliver USD 100, leaving the starting USD 50 debit outstanding. The ledger's funding path can overwrite a negative balance with zero. Keep signed balances throughout the calculation. Fund a new order only from proceeds available after covering the applicable shortfall. Verify the two currency directions, positive balances, and that replaying the final instructions agrees with the ledger. [Cash ledger](src/rebalancer.py) · [Conversion math](src/fx_math.py)

**13. Show the current reference high immediately after recovery.** With a frozen high of 100 and a recovery value/new high of 110, the transition to baseline displayed the next −10% trigger at 90. The next baseline run uses 99. When recovery clears the frozen reference, build the returned posture, drawdown and next trigger from the baseline high and date. Two evaluations at the same value should agree on those fields. [Tactical evaluation](src/tactical.py) · [Recovery tests](tests/test_tactical.py)

**14. Reject tactical thresholds the state machine cannot reach.** Four distinct deployment thresholds parse successfully, but a drawdown past all four stops at level three. Likewise, a recovery percentage with no matching regime can be displayed as a baseline trigger while evaluation skips it. Build the deployment levels from the configured thresholds, including a fourth level. Validate that each recovery leads to a reachable, less-deployed level at load time. Test a fourth threshold, an unmapped recovery target, and a valid shorter configuration. [Tactical parser and regime lookup](src/tactical.py)

For **7**, include the report path where a currency conversion is the only instruction. With CAD 37.49, zero USD, a USD 30 holding and a CAD 10.49 fee, the end-to-end fixture produced no ETF trade and a two-share DLR sweep. The report omitted the projected allocation because it checks only the trades list. Build the final projection whenever a conversion changes cash and verify the resulting cash weights and fee. [Report assembly](src/report_builder.py)

**19. Reserve one fee when a sweep extends an existing journal.** An account with CAD 37.49 and USD 20 buys one USD 30 ETF share. At CAD 13.50 per DLR share, USD 10 proceeds per share and a CAD 10.49 fee, the required conversion buys one DLR share. The remaining CAD 13.50 can buy a second share in the same journal, but the sweep reserves the fee again and stops at one. Size the combined instruction from the whole available source balance, accounting for its single fee in the currency where it is charged. Verify the final instruction buys two shares, spends exactly CAD 37.49 including the fee, and leaves USD 10 after the ETF purchase. Cover a standalone sweep, a balance one cent below the threshold, and a USD-to-CAD journal where the fee comes out of CAD proceeds. [Conversion sizing and sweep](src/fx_conversions.py) · [Conversion tests](tests/test_fx_conversions.py)

## Operations and small refactors

**8. Use one DLR quote snapshot per interactive report.** The rate lookup and conversion sizing repeat the same two symbol searches and two quote requests. Fetch the pair once and use its validated rate and bid/ask prices throughout the run. A counting fake should see four requests instead of eight. A bad rate must still stop valuation. [Interactive entry point](main.py) · [Quote lookup](src/fx_rate.py)

**15. Measure a prolonged sync failure by elapsed time.** The template estimates hours by counting completed failed runs. Manual dispatches can satisfy the count in minutes, and a dependency installation or push failure produces a message telling the user to replace their tokens. Use run timestamps to measure the failure period, include the current failure, and name the failed operation when known. Verify rapid manual retries, an outage over 48 hours, repeated failures with an open issue, and recovery. Changes to the public template need a separate rollout to the private workflow. [Workflow template](templates/private-state-repo/portfolio_sync.yml)

**16. Remove redundant work when touching the affected modules.** The FX resolver rewrites encrypted state even when the resolved split is identical. Compare the new mapping with the loaded one before saving. The planner's only caller of `_account_buyable_candidates` always passes `underweight_only=False`. Remove the unused mode and retain the restriction on buying an at-target restricted holding. Verify the unchanged and changed FX cases, and keep the affordability and cascade-ranking tests passing. [FX state](src/fx_targets.py) · [Candidate selection](src/rebalancer.py)

## Decisions and verification

- **Brokerage cash always targets 0%.** As part of finding 5, remove the explicit CAD and USD zero entries from the example and private settings together. Reserve both currency codes wherever an allocation rule can assign a target. An explicit cash target should give a clear instruction to remove it. Both run modes must measure actual CAD and USD balances and their drift against an implicit zero, and the planner should continue deploying available cash. Verify that migrating existing zero entries preserves allocations and trades, and that a configured positive cash weight is rejected. External savings accounts such as Saven retain their own allocation targets. [Config loader](main.py) · [Example configuration](config/settings.example.yaml) · [Planner rules](docs/rebalancer.md)
- **Drift alerts use the displayed score.** Keep the existing one-decimal output for both the report and the workflow comparison. A displayed 95.0% opens or retains the alert, and 95.1% clears it. This requires no precision change. [Score output](main.py) · [Alert comparison](templates/private-state-repo/portfolio_sync.yml)
- **Transfer verification.** A read-only statement replay confirmed that a posted source withdrawal and matching transit preserve household value while leaving actual brokerage cash unchanged. Replaying the same export also preserved transit. Final live verification requires the destination posting. Verify that the receipt enters actual cash once, clears matching transit, and remains settled on replay. [Transfer contract](docs/external-accounts.md) · [Transfer scenarios](tests/test_transfer_tracking.py)
- **Redemption evidence remains separate.** Preserve tests for blocked sales and expiry of broker history. Verify broker visibility of a pending redemption against a real redemption request before specifying detection. [Redemption tests](tests/test_redemption.py)

Implementation verification used the full Python suite, disposable Git remotes, a real SOPS binary and a disposable age identity. The workflow alert scripts were exercised with simulated run histories. A production OAuth exchange and the deployed scheduled workflow require live verification.
